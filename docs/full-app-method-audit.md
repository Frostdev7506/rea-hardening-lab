# Full-application paired follow-up: method audit

Reviewed 6 November 2026 using the Matt Pocock research workflow and primary local source. This review inspected the protocol, runner, HTTP grader, independent objective verifier and original application source. It did **not** inspect either reconstruction, private trial directories, trial logs, reports or scores, or contact the reconstruction agents. No trial result is asserted here. No issue found in this source review requires interrupting the ongoing attempts.

## What this design can answer

The design is a useful **exploratory, REA-assisted paired reconstruction**: one fresh CLI session gets the original dispatch artifacts, another gets their hardened counterparts, with the same prompt, 900-second ceiling, requested model/reasoning setting, scaffold, dependencies, shared quote artifacts and presentation aids. The first completed app is submitted before external checks. Direct inspection and isolated decoding are explicitly allowed alongside mandatory REA use. It therefore evaluates the combined analyst workflow; it does not isolate REA alone or compare REA against a workflow without REA. [Frozen protocol](../evidence/full-app/protocol.json), [prompt and scaffold](../scripts/full-app-pair.mjs#L20-L79), [launch and timing](../scripts/full-app-pair.mjs#L84-L113).

There is **one independent reconstruction per arm**, not 312 independent experiments. The 312 cases are probes of each submitted app. Differences can describe these two attempts under this budget, but cannot estimate a model-wide success rate, causal average hardening effect or statistical confidence. Serialized order was selected once and frozen as before then after; it is randomized order, not counterbalancing across replications. The older three-per-arm planner-only trials have a different target and must remain separate. [Protocol](../evidence/full-app/protocol.json), [order selection](../scripts/full-app-pair.mjs#L49-L50), [original planner-only target](../evidence/v2/collection.json).

## Confirmed strengths

- **The treatment is matched at the supplied-code level.** Exactly the four primary dispatch chunks are selected from original versus hardened snapshots. All four quote chunks and both CSS files have identical recorded hashes across arms. Screenshots are copied from the same paths for both arms. The shared quote chunks are checked for several dispatch-specific strings to guard against an obvious unprotected dispatch duplicate. The quote feature is correctly declared secondary because it is outside the treatment. [Input collection](../scripts/full-app-pair.mjs#L62-L82), [recorded hashes](../evidence/full-app/protocol.json).
- **The frozen planner reference is sound for its declared fixture.** A read-only replay in this review verified the committed SHA-256, 312 rows and **312 distinct scenarios**, then independently recomputed all **312 objective values** and checked all reference plans for route/resource/timing/arithmetic feasibility. The second solver uses Floyd–Warshall, route-prefix enumeration and disjoint-mask dynamic programming rather than calling the application's search. It shares the trusted fixture, which is appropriate for checking recovery of this fixed application. [Freeze](../scripts/full-app-pair.mjs#L33-L46), [independent solver](../scripts/v2-oracle.mjs), [feasibility verifier](../scripts/v2-grade.mjs), [original solver](../src/lib/dispatch-engine.ts).
- **Exact behavior and planning semantics are reported separately.** Exact HTTP comparison covers status, JSON response type, Cache-Control and normalized body. The separate semantic score validates the full road path, service times, load, compatibility, shifts, penalties and optimum, accepting equally optimal feasible alternatives. A tie-break difference can reduce exact fidelity without being a mathematically incorrect plan. [Comparison](../scripts/full-app-check.mjs#L21-L50), [case grading](../scripts/full-app-check.mjs#L105-L115), [verifier](../scripts/v2-grade.mjs).
- **Persistence is exercised through production HTTP, with important conflict cases.** The checks include save/read/commit, retry identity, competing drafts, same-courier conflict despite disjoint shipments, empty-plan rejection and restart reads. These reflect real transaction/reservation rules in the source. The clone is a separate production process with protected owner repositories and the peer directory denied, plus outbound network limited to its own localhost port during grading. [Workflows](../scripts/full-app-check.mjs#L148-L232), [store](../src/lib/dispatch-store.ts), [runtime containment](../scripts/full-app-check.mjs#L52-L61).

Focused source-side tests passed **3/3** (`node --test test/full-app-check.test.mjs test/v2-grade.test.mjs`). This includes normalization checks, rejection of invalid paths/timing/costs and acceptance of an alternative optimal courier assignment. No reconstruction was executed by this reviewer. [Normalization test](../test/full-app-check.test.mjs), [planner tests](../test/v2-grade.test.mjs).

## Findings and reporting requirements

### 1. REA compliance and completed build must be verified, not inferred from a report file

The prompt mandates a real REA CLI invocation, but the runner only copies `rea-analysis.json` if present and accepts its absence. It does not assert that an actual analyze command ran, that the report parses, which primary files it covered, whether the scan hit limits, or whether the candidate built successfully. The number of completed shell commands is not that evidence. The same applies to the self-contained-source requirement: the prompt prohibits executing/importing supplied compiled artifacts, but the grader does not itself scan the candidate for that dependency. [Requirement](../scripts/full-app-pair.mjs#L24-L28), [REA command and permitted scan subsets](../scripts/full-app-pair.mjs#L78-L79), [collection after exit](../scripts/full-app-pair.mjs#L104-L112).

After submission, retain actual command events, complete reports, scan coverage/limits, successful build output and the source/runtime hashes; audit that supplied compiled artifacts are not loaded at runtime. If either arm skipped REA, label that attempt noncompliant rather than calling the pair an REA-assisted comparison. A report's size or a partial static scan is a diagnostic, not a correctness measure or proof of REA's contribution. This is an evidence gate, not a reason to send either analyst feedback.

### 2. Runtime filesystem isolation is narrower than reconstruction-session isolation

The reconstruction CLI profile denies owner repositories, earlier recovery control, sessions, memories, peer directory, both trials' private log files and history. The production clone profile denies the repositories, earlier recovery control and peer directory, but **omits sessions, memories, history and the sibling private log files**. Both profiles begin with `allow default`; neither is an exclusive trial-directory filesystem boundary. The CLI's filesystem probes are meaningful permission-error checks, while the runtime profile has no equivalent probe in this script. [CLI profile and probes](../scripts/full-app-pair.mjs#L88-L97), [runtime profile](../scripts/full-app-check.mjs#L52-L61).

The source therefore supports “protected owner repositories and peer directory denied during production grading,” not “the same complete private-root/log denial policy at both stages.” This is a possible contamination path, not evidence of any access by a candidate. Audit frozen source for such reads; if a stronger runtime policy is applied before grading, retain it and its successful probes as a grader-environment correction, without modifying the submissions. Network avoidance during reconstruction remains instructional; production grading adds the explicit outbound restriction. [Protocol disclosure](../evidence/full-app/protocol.json).

### 3. Workflow passes establish selected invariants, not complete response parity

The 312 draft-creation checks use the full normalized response comparator. Several workflow checks instead test only selected fields or status codes. For example, reservation exclusion asserts zero delivered and one remaining shipment; competing-draft checks assert one 200/one 409 and unchanged loser, but do not compare the conflict error body; simultaneous retries assert 200, two events and identical replies within each app. These are valuable invariants, but successful checks can still miss wrong scenario/plan metadata, reserved-courier lists or error bodies in those paths. The base save/commit and disjoint-courier-conflict checks do compare normalized records/errors. [Workflow assertions](../scripts/full-app-check.mjs#L148-L205), [observable saved record](../src/lib/dispatch-types.ts#L11), [commit/error behavior](../src/lib/dispatch-store.ts), [record route](../src/app/api/plans/%5Bid%5D/route.ts).

Report category passes as the **tested workflows**, not blanket exact parity for every state transition. The replanning path is not independently optimized/feasibility-graded under arbitrary reservations: the 312 semantic checks all submit `batchId: null`; reservation behavior has a small explicit workflow set. [Fresh-case requests](../scripts/full-app-check.mjs#L105-L115), [reserved model filtering](../src/app/api/plans/route.ts).

### 4. Timestamp and ID normalization removes more than random differences

IDs are validated as lowercase v4 UUIDs, and creation timestamps are checked near the request. Quote expiry is checked near ten minutes. However, event times are only required to be parseable before removal: their order, equality of the initial planned time to `createdAt`, and proximity of commit time to the commit request are not verified. A source-side probe confirmed that normalization accepts a planned event in 1970 followed by a committed event in 1960. There is also no explicit cross-creation uniqueness assertion for IDs or new batch IDs. [Normalization and creation checks](../scripts/full-app-check.mjs#L21-L50), [source event creation](../src/lib/dispatch-store.ts).

This is a bounded false-positive risk in timestamp/identity fidelity, not a defect in plan mathematics. Say “UUID formats and selected timestamp bounds checked; nondeterministic values normalized.” Do not claim every property of randomly generated IDs/timestamps has been preserved.

### 5. Restart persistence is stronger than memory-only success, but SQLite storage is only partially attested

The restart checks compare saved records after restarting both production processes and verify the first 16 bytes of the clone's declared database files. This rejects a purely in-memory implementation and an absent SQLite file. It does **not** prove those records or reservation constraints are actually stored in SQLite: a candidate could use a different durable store while creating an empty SQLite file. The post-restart checks retrieve records but do not attempt new competing commits/replans in their batches, so durable reservation enforcement is not separately demonstrated. [Restart checks](../scripts/full-app-check.mjs#L216-L232), [actual SQLite payload/reservation schema](../src/lib/dispatch-store.ts#L10-L18).

Use “saved-record durability plus SQLite-file signature” unless a post-submission source/schema audit establishes SQLite-backed records and reservations. Such an audit can strengthen the evidence without giving an analyst repairs or feedback.

### 6. UI and validation coverage need separate, explicit limits

The HTTP check's saved-query assertion looks for the plan ID and a dispatched label in raw HTML; it does not establish restored controls, route overlays, history navigation, dirty-state suppression, responsive layout, keyboard operation or live commit behavior. Those are real observable parts of the original app. Browser checks are deliberately described as separately recorded, so they must exist before claiming the entire UI was faithfully rebuilt. A screenshot resemblance score alone cannot replace interaction checks. [Saved-query test](../scripts/full-app-check.mjs#L160-L165), [separate-browser disclosure](../scripts/full-app-check.mjs#L236), [original interactions](../src/app/dispatch-board.tsx).

Dispatch validation probes cover useful representative errors, including UTF-8 byte size, time boundaries and unknown fields, but they are not exhaustive contract coverage. Legacy quote checks reuse 42 pricing/eligibility cases plus save/book/restart; they do not cover its expired-booking 410 path or all malformed HTTP inputs. Keep legacy results secondary and avoid “all routes/errors matched” language. [Dispatch probes](../scripts/full-app-check.mjs#L117-L139), [dispatch parser](../src/lib/dispatch-request.ts), [stream limit](../src/lib/request-json.ts), [quote cases](../test/scenarios.mjs), [quote expiry path](../src/app/api/quotes/%5Bid%5D/route.ts#L13-L18).

### 7. Aggregate counts and effort require careful interpretation

The frozen 312 scenarios contain **82 zero-delivery**, **230 positive-delivery** and **145 multi-courier** plans. Closure counts are: 0 roads 194 cases; 1 road 42; 2 roads 25; 3 roads 18; 4 roads 18; 5 roads 6; 6 roads 7; 8 roads 2. Start times span 480–720. Report this distribution or stratified results so easy empty outcomes do not obscure delivery failures. The cases are fresh and unique, but they are neither a uniform sample of all valid scenarios nor a population of independent reconstruction attempts. [Case generator](../scripts/full-app-pair.mjs#L33-L44), [committed reference hash](../evidence/full-app/protocol.json).

Do not add exact and semantic counts as independent successes; they examine the same submitted plan. Workflow failures can cascade: `durablePlans` and `durableQuotes` are established by earlier tests, and later tests explicitly depend on them. Preserve individual errors and distinguish a failed prerequisite from an independently observed durability or UI defect. [Dependency and aggregation](../scripts/full-app-check.mjs#L147-L236).

The wall clock includes launch, investigation, REA, implementation, build and self-checks. A shorter submission with lower fidelity does not establish that recovery was easier, and a 900-second timeout is a censored observation. Token usage is taken from the last completed turn and can be unavailable on interrupted runs; missing usage is not zero. Audit retained events before comparing totals, report correctness alongside effort, and keep requested model alias distinct from backend identity. No dollar-cost or stable recovery-rate inference follows from this pair. [Timing, usage and identity note](../scripts/full-app-pair.mjs#L98-L107), [frozen effort statement](../evidence/full-app/protocol.json).

## Required closeout evidence

Before publishing a verdict, verify both attempts' REA/build/source compliance; preserve input and submission hashes, actual executable/build identity, fresh session IDs, timeout state and available token counters; retain browser interaction evidence and source-level persistence checks; and verify the original runtime still matches the committed reference. The grader already asserts all 312 baseline plan outputs match before scoring their corresponding candidate responses, which protects the primary planner comparison against a stale baseline. Its `runtime-original` directory is cached if present, so source provenance for other behavior still needs retained build/runtime evidence. [Reference guard](../scripts/full-app-check.mjs#L105-L107), [baseline construction/cache](../scripts/full-app-check.mjs#L76-L84), [submission copy](../scripts/full-app-pair.mjs#L108-L112).

Supported wording after those checks is: “In one matched 15-minute REA-assisted full-application attempt per artifact variant, the original/hardened submissions achieved [separate exact, semantic, workflow and browser results] with [observed effort].” Whether this pair suggests reduced accuracy, greater effort, both, or neither must follow the results. It does not establish that die-a-rea generally prevents reconstruction or generally has no effect.

## Post-submission closeout by the experiment owner

The review above is preserved as a source-only audit, not rewritten around the observed outcome. The closeout is in [the full-app evidence guide](../evidence/full-app/README.md).

Actual command events and parsed REA reports confirm both scans; successful production builds are retained in each execution audit. Frozen source trees match their first-final copies and contain independent recovered modules rather than supplied-bundle execution or an original-server proxy. Runtime containment was strengthened to deny sessions/memories/history/logs as well as source/peer roots; own-loopback outbound was tested separately. Neither candidate was edited or given grading feedback.

Event timing assertions, direct SQLite ID inspection, post-restart reservation checks and equal clock-advanced quote expiry were added to the external harness. An initial Date-hook failure was fixed and retained in control history. A port guard now refuses occupied listeners, with a regression test. Final control passed 396/396; A passed 396/396; B passed 342/396, with 54 exact and independently suboptimal dispatch cases. Actual hardened-original behavior passed all 312 fresh cases. Selected workflow assertions remain narrower than complete transition response parity; fresh-batch planning and finite browser coverage are explicitly scoped.

Both actual REA scans emitted valid JSON then failed process-table cleanup in the sandbox, and both shells resolved unsupported Node patch 24.13.1. Supported Node24.22.2 post-submission scans outside the sandbox exited zero for both. Process-list denial was independently reproduced without retaining process data. This shared environment issue is disclosed, not attributed to hardening; later scans did not replace trial effort or feed candidates. Requested backend alias remains distinct from independently verified identity.

The protected source's incumbent-cost comparisons explain the failures: a separate in-memory diagnostic repair matches 312/312 while the official submission stays unchanged at 258/312. Browser evidence reproduces the 09:30 mismatch. A has a verified 390px screenshot; B's attempted override did not apply, so no responsive pass is claimed there. The one-pair effort comparison and earlier function-only replications remain separate.
